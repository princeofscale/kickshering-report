# 21. Passive-capture workflow (nRF Sniffer + Wireshark)

[← Назад к индексу](../README.md)

Пассивный захват — единственный путь поднять крипто/авторизационные утверждения по лестнице
доказательности ([§20.2](20-methodology-upgrades.md#202-evidence-ladder-ad--обязательный-артефакт)).
Это **дополнение** к iPhone-инструментам (те дают GATT/ADV read-only снапшоты; сниффер даёт
трассу handshake). Требует внешнего железа — это уже не «только iPhone».

## 21.1 Границы (обязательно)

- Захватывается **только легитимный** трафик: соединение, инициированное **официальным**
  приложением (ваш аккаунт) с **вашим собственным** устройством или вашей активной арендой.
- Сниффер **пассивен**: он слушает эфир, ничего не отправляет в устройство. Никаких
  инъекций/replay в сторону устройства.
- Никаких попыток захватывать/расшифровывать чужие сессии.

## 21.2 Оборудование и софт

- BLE-сниффер: Nordic **nRF52840 Dongle** (или nRF52-DK) с прошивкой **nRF Sniffer for
  Bluetooth LE**.
- **Wireshark** с плагином nRF Sniffer.
- Телефон с официальным приложением (Whoosh/Urent) и вашим аккаунтом.
- Ваше устройство/активная аренда.

## 21.3 Процедура

1. Запустить Wireshark + nRF Sniffer, выбрать целевое устройство по **advertising** (сверить с
   маркерами из [§16](16-ble-protocol-reference.md): имя `MISc`/`NBSc`, service UUID Family A/B,
   ASCII-маркер `696e65626f74`).
2. Начать захват, затем в официальном приложении выполнить **легитимное** подключение (свой
   аккаунт, своё устройство). Захватить **полный** цикл: advertising → connection → GATT
   discovery → `PRE_COMM` → `SET_PWD` → `AUTH` → (пост-auth сообщения, если есть).
3. Повторить **3–5 раз** (разные сессии подключения того же устройства) — для анализа
   энтропии/повторов challenge и монотонности счётчиков.
4. Сохранить каждый захват как `.pcapng` с метаданными: модель, FW, SN-маска, дата/время, версия
   приложения, телефон/OS.

## 21.4 Wireshark-фильтры

- BLE advertising: `btle.advertising_header`; сузить по Company ID в `btcommon.eir_ad...`.
- Наши сервисы/характеристики (по `handle` после discovery):
  - Family A: write `…0002`, notify `…0003`.
  - Family B: write `…0002`, **notify `…0004`** (не `…0003`).
- GATT write/notify: `btatt.opcode` (write req/cmd, handle value notification).
- По значению: искать структуру фреймов Ninebot (`55 AA` / `5A A5`, см.
  [§16.3](16-ble-protocol-reference.md#163-пакетный-формат-classic-verified)).

## 21.5 Reconstruction cross-check (ступень C→D)

1. Сопоставить **каждый** захваченный байт handshake с логикой открытых реализаций:
   `ownbee/ninebot-ble` (miauth), NootNooot docs, `py9b` — **построчно**.
2. Составить **таблицу расхождений** трёх реализаций (имена полей, смещения, длины, логика MAC,
   IV/counter). Где они расходятся или делают необоснованные допущения (comments vs code) —
   пометить как **UNCONFIRMED**.
3. Офлайн вычислить сессионные ключи из захваченных полей и проверить, что они объясняют **всю**
   зашифрованную/аутентифицированную часть **без подгонки**. Только тогда — ступень C.
4. Повторяемость на ≥2 устройствах/захватах и согласие ≥2 реализаций без противоречий —
   ступень D.

## 21.6 Что этим можно и нельзя доказать

- **Можно (безопасно):** структуру Encryption2, длину/энтропию challenge, наличие counter/
  anti-replay (по наблюдению монотонности), уникальность ключей на устройство (cross-device),
  где реально проходит аутентификация.
- **Нельзя (и не нужно):** доказать уровень E/F (реальное исполнение привилегированной команды
  вне сессии) — это потребовало бы write в устройство; вне scope на прод/чужом/арендованном.
  Вывод об авторизации строится из **наблюдаемого** поведения (принимает/отвергает, тайминги,
  ошибки), а не из инъекций.
