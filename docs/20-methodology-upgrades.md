# 20. Методологический апгрейд (evidence-first, фальсифицируемость, контроли)

[← Назад к индексу](../README.md)

Принято по итогам внешнего методологического аудита. Эти правила **имеют приоритет** над
удобством и применяются ко всем разделам отчёта и ко всем полевым результатам.

## 20.1 Passive-capture-first (главное правило)

Любая гипотеза о device-side authorization проверяется **сначала пассивным захватом** легитимного
трафика (nRF Sniffer + Wireshark, см. [§21](21-passive-capture-workflow.md)), а не отправкой
write-пакетов в устройство. Активные write-эксперименты к прод/чужому/арендованному устройству
**запрещены** и не приближаются даже на собственном железе без отдельного обоснования.

## 20.2 Evidence ladder (A–D) + обязательный артефакт

Ни один вывод не поднимается выше **POSSIBLE**, пока к нему не привязан артефакт. Крипто- и
авторизационные утверждения проходят лестницу:

| Ступень | Что значит | Требуемый артефакт |
|---|---|---|
| **A — Observed (raw)** | Сырой захват + условия + устройство (own) | `.pcapng` / GATT JSON + метаданные (модель, FW, SN-маска, время, место) |
| **B — Parsed** | Структурный парсинг совпал с ожидаемым **без ручной подгонки** | таблица frame → phase → field |
| **C — Reconstructed** | Независимое офлайн-воспроизведение даёт те же байты | offline reconstruction + формулы + вывод |
| **D — Cross-validated** | Воспроизводится на ≥2 своих устройствах / ≥2 захватах / согласуется между ≥2 реализациями (NootNooot / ownbee / py9b) **без противоречий** | сравнительная таблица «source → assertion → evidence» с ссылками на файлы/коммиты |

Переход крипто-утверждения из PROBABLE к «приближению к CONFIRMED» возможен **только после D**, и
только если наблюдаемое поведение непротиворечиво объясняется схемой во всех наблюдённых фазах.

## 20.3 Фальсифицируемость (pre-registration)

Перед объявлением любого «подтверждения» заранее записать **фальсифицируемое** предсказание —
и H1, и H0:

- **H1 (баг):** существует наблюдаемая последовательность BLE-сообщений, после которой устройство
  выполняет чувствительную функцию **без** действующей rental-сессии.
- **H0 (нет бага):** устройство принимает такие сообщения **только** в контексте сессии,
  созданной легитимным потоком (backend → app → device), и это состояние прослеживается в трассе.

Заранее определить **минимальный набор артефактов**, при отсутствии которых гипотеза остаётся
UNCONFIRMED. Записать, какое наблюдение опровергло бы гипотезу.

## 20.4 Negative controls (для diff «до/после аренды»)

Улучшенный протокол — см. [§15.5](15-field-testing-guide.md). Кратко, обязательны:
1. **Null hypothesis:** «rental-state НЕ отражается в читаемых характеристиках GATT». Идентичный
   снапшот — это **ожидаемый** результат, а не провал теста.
2. **3–5 снапшотов** в каждом состоянии, с фиксацией порядка чтения и вариаций `handle`.
3. **Контроли:** (а) то же устройство дважды в «не арендовано»; (б) consumer-аналог той же
   модели/FW, где уместно; (в) журнал времени + стабильность advertising.
4. **Структурный diff** (поля/permissions/descriptors/типы значений), с явной фиксацией даже
   **неизменных** блоков («no change observed»).
5. **Advertising тоже:** `Manufacturer Specific Data`, `Service Data`, `Flags`, имя — до
   подключения (пассивно). Состояние часто отражается в ADV, а не в GATT.
6. **Логировать конфаундеры:** телефон, OS, версия приложения, заряд, гео, время, события
   connect/disconnect.

## 20.5 Дисциплина классификации

- **Vendor Claim (unverified):** заявления оператора/вендора («BLE-доступ невозможен») маркируются
  отдельным тегом и **никогда** не используются как доказательство/опровержение технической
  гипотезы.
- **«Отсутствие доказательств ≠ доказательство отсутствия»:** формулировка вывода всегда
  «нет публичных воспроизводимых доказательств в пользу гипотезы для флотов Whoosh/Urent», а не
  «гипотеза опровергнута».
- **Extrapolation Assumption:** любой перенос (consumer→rental, модель→модель, FW→FW) сопровождается
  явным столбцом **Assumption** с конкретным обосновывающим наблюдением; без него перенос
  помечается как **unjustified extrapolation = POSSIBLE/UNCONFIRMED**.
- **Разделение доменов/протоколов:** Ninebot rental vs consumer vs другие вендоры (Äike/Yadea/Zero/
  Okai) — не смешивать; Okai держать в отдельном scope.

## 20.6 Responsible disclosure — документальный поиск, а не предположение

Правило: отчёт фиксирует **результат поиска** (found: yes/no, URL, дата, HTTP-статус), а не вывод
«вероятно существует/отсутствует».

**Результат поиска на 2026-09-03 (этой сессии):**
- Прямые проверки `https://whoosh.ru/.well-known/security.txt` и
  `https://urent.ru/.well-known/security.txt` — **не выполнены из этой среды**: доступ к доменам
  заблокирован egress-прокси (не 404, а сетевое ограничение стенда).
- Общий web-поиск публичной bug-bounty/RD-программы Whoosh / Urent / МТС Юрент — **совпадений не
  найдено** (выдача — общие материалы про bug bounty, без этих организаций).
- **Статус: UNCONFIRMED.** Нельзя утверждать ни наличие, ни отсутствие. **Действие для вас (с
  неограниченной сети):** проверить `/.well-known/security.txt` на `whoosh.ru`, `urent.ru`,
  доменах МТС; страницы «Безопасность»/«Ответственное раскрытие»; профили на HackerOne/Bugcrowd/
  Standoff365/BI.ZONE Bug Bounty; и зафиксировать found/not-found с URL + датой + скриншотом.
  До появления официального канала — раскрытие только приватно (security@ / поддержка), без
  публичных подробностей.
