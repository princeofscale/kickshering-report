# Tools — read-only BLE inspection

[← Назад к индексу](../README.md)

Этот каталог содержит инструменты для **пассивной / read-only** проверки BLE-поверхности
атаки, описанной в [`docs/`](../docs/00-scope-and-methodology.md). Оба инструмента (iOS-
приложение и Python-скрипты) намеренно **не реализуют write-путь** к GATT-характеристикам —
это архитектурное решение, а не просто договорённость: в коде физически нет функции записи
на характеристику устройства.

## Что здесь есть

| Инструмент | Где запускается | Что делает |
|---|---|---|
| [`ios-app/`](ios-app/README.md) | iPhone (через Xcode) | Пассивный BLE-скан + read-only GATT enumerate/read, экспорт JSON |
| [`scripts/ble_passive_scan.py`](scripts/README.md) | macOS/Linux/Windows laptop (опционально) | То же пассивное сканирование advertising, для кросс-проверки/автоматизации |
| [`scripts/ble_gatt_enumerate.py`](scripts/README.md) | macOS/Linux/Windows laptop (опционально) | Read-only connect + enumerate одного устройства по адресу |
| [`scripts/analyze_gatt_log.py`](scripts/README.md) | где угодно (офлайн, без BLE) | Разбор экспортированного JSON-лога → Markdown-таблица; diff до/после аренды |

iOS-приложение — основной инструмент, раз у вас iPhone. Python-скрипты — опциональное
дополнение, если у вас также есть ноутбук (например, для автоматизации серии сканирований или
для интеграции с BLE-снифферами).

## Правила безопасности (обязательны к соблюдению)

1. **Только собственное оборудование или собственная активная оплаченная аренда.** Никогда —
   чужой припаркованный самокат, который вы не арендовали (для пассивного Шага A из
   [Field Testing Guide](../docs/15-field-testing-guide.md) наблюдение advertising допустимо
   рядом с любым устройством, т.к. не отличается от того, что делает любой смартфон рядом; но
   **connect** — только на своём/арендованном вами).
2. **Никогда не добавляйте write-функциональность** в эти скрипты и не используйте сторонние
   инструменты для записи в характеристики устройства, которое вам не принадлежит или не
   находится под вашей действующей арендой.
3. Если вы нашли характеристику, похожую на unlock/control/motor (по UUID, имени сервиса, или
   по наличию `write`/`writeWithoutResponse` в properties) — зафиксируйте только метаданные
   (UUID, properties) в логе. Не читайте её содержимое повторно бессмысленно, не пытайтесь её
   записать.
4. Логи (`logs/`) могут содержать серийные номера / MAC-адреса устройств — прежде чем делиться
   логом публично (например, в bug bounty репорте), убедитесь, что это не раскрывает
   персональные данные третьих лиц (например, если в advertising случайно попало имя,
   привязанное к чужому аккаунту — маловероятно для этих устройств, но проверяйте).
5. Все идентифицированные находки должны сначала пройти через таблицу уровней A–G в
   [`docs/10-safe-poc-methodology.md`](../docs/10-safe-poc-methodology.md) — не переходите к
   уровням E/F/G на реальном устройстве.

## Известные ограничения этой версии инструментов

- Нет packet sniffing в реальном времени (нужен отдельный оборудование, напр. Nordic
  nRF Sniffer for Bluetooth LE + Wireshark) — не входит в эту ревизию, так как требует
  дополнительного HW-дongle, а не только iPhone/laptop. Если у вас есть такой сниффер, GATT
  UUID'ы, полученные из `tools/`, помогут вам отфильтровать нужный трафик в Wireshark.
- iOS-приложение не может обойти iOS Bluetooth permission/pairing UX — это ожидаемо и
  специально не обходится (обход системных permission diалогов не входит в задачи этого
  исследования).
- Оба инструмента READ-ONLY по дизайну — если для более глубокой проверки понадобится write
  (например, доказать уровень E на **строго собственном, лабораторном** устройстве), это
  осознанно оставлено за рамками автоматизированных скриптов репозитория: такой шаг должен
  выполняться вручную, разово, с полным пониманием последствий, и никогда — на арендованном
  или чужом устройстве.
